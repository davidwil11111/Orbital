## New finding: non-ASCII command output becomes `?` (pre-existing, also on main)

On this machine **every** non-ASCII character in shell output arrives as `?`, in both sandboxed and
run-as-user commands: `Write-Output "中文测试"` → `????`, `cmd /c "echo 中文测试"` → `????`, Desktop
names `剪映专业版.lnk` → `?????.lnk`, `PPT模板` → `PPT??`, `®` → `r`.

Cause: the `.ps1` runs under `powershell -File … > out.txt`. With redirected output, PowerShell 5.1
encodes with `[Console]::OutputEncoding`, which is the OEM code page (437 here, because the system
locale is en-US). CJK can't be represented, so it is already `?` in the file that
`windows/process.py` reads as UTF-8. On a zh-CN system locale (cp936) the bytes would be GBK and the
UTF-8 read would give mojibake (`�`) instead. `main` has no encoding handling either (inline
`-Command`), so this is not a batch regression.

**Fixed on this branch (uncommitted at time of writing):** `build_windows_script()` now starts with
`try { $OutputEncoding = [Console]::OutputEncoding = New-Object System.Text.UTF8Encoding $false } catch {}`,
and the run-as-user path decodes with `encoding="utf-8", errors="replace"` (it used `text=True`
alone, which means the locale code page). The sandboxed path already read its files as UTF-8.
Tests: `test_windows_shell_wrapper.py` adds the preamble check, the run-as-user decode check, live
`Write-Output 中文` / `cmd /c "echo 中文测试 ®"`, and a live worker-path redirect check. All failed
before the fix and pass after. `test_subprocess_encoding.py` drops `shell.py` from its exempt
allowlist (0 exempt sites now). Live, source daemon on the installed app's data: in `bench114` (safe
mode, worker) and `open117` (open, as user) `Write-Output "中文测试 ®"` and `cmd /c "echo 中文测试 ®"`
return `中文测试 ®`, and the Desktop listing shows `剪映专业版.lnk`. Side effect: PowerShell error
positions now say `ps1:2` instead of `ps1:1` for the command line.
